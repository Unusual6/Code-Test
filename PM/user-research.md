# 用户研究与需求验证

> 目标：在投入设计和开发之前，弄清楚目标用户、真实问题及其证据强度。

## 1. 从假设开始

先把模糊想法拆成可验证的假设，避免访谈变成收集功能愿望。

| 假设类型 | 需要回答的问题 | 示例 |
|----------|----------------|------|
| 用户 | 谁会遇到问题？哪些人不会？ | 每周处理大量报销单的财务人员 |
| 场景 | 问题在何时、何地发生？ | 月末集中核对多来源票据 |
| 问题 | 用户现在如何完成任务？最难的部分是什么？ | 手工逐项比对，容易遗漏 |
| 价值 | 问题造成什么可观察的损失？ | 处理耗时增加，错误需要返工 |
| 方案 | 哪种改变可能改善结果？ | 自动提取字段并提示差异 |

### 假设记录模板

```markdown
## 假设：[一句话描述]
- 目标用户：
- 使用场景：
- 当前行为/替代方案：
- 预期问题与影响：
- 可能方案：
- 支持证据：
- 反例或不确定点：
- 验证方式与通过标准：
- 负责人 / 截止时间：
```

## 2. 选择研究方法

| 方法 | 适合回答 | 不适合单独回答 |
|------|----------|----------------|
| 用户访谈 | 动机、流程、例外情况、替代方案 | 市场规模、精确发生率 |
| 问卷 | 已知问题的分布与分群差异 | 探索未知动机、因果关系 |
| 行为数据分析 | 用户做了什么、在哪一步流失 | 用户为什么这么做 |
| 可用性测试 | 用户能否理解并完成具体任务 | 是否存在足够强的市场需求 |
| 日记研究 / 情境观察 | 真实环境中的长期行为与变通方式 | 快速获得大样本结论 |
| 客服与销售记录 | 高频抱怨、阻塞与现有解决办法 | 代表全部用户群体 |

重要决策尽量交叉验证不同来源。单一客户的强烈意见是线索，不等于总体结论。

## 3. 进行问题访谈

### 访谈前

- 明确研究问题和目标用户筛选条件。
- 准备开放式问题，避免暗示受访者认可方案。
- 说明研究目的、记录方式和数据使用范围，并取得同意。
- 先访谈近期真实经历过该场景的人。

### 问题示例

- 请回忆最近一次完成这件事的过程，从哪里开始？
- 哪一步最花时间，发生了什么？
- 遇到问题时你怎么处理？还有谁参与？
- 你现在用什么工具或办法绕过这个问题？
- 最近一次问题造成了什么后果？
- 这件事多久发生一次？哪些情况下不会发生？

避免直接问“你会不会用这个功能”或“你觉得这个想法怎么样”。假设性意愿通常弱于过去行为证据。

### 访谈记录

```markdown
## 访谈：[用户代号] / [日期]
- 用户类型与筛选依据：
- 最近一次目标场景：
- 实际步骤：
- 主要困难及频率：
- 当前替代方案：
- 问题后果：
- 原话摘录（去除可识别个人信息）：
- 与原假设不一致的证据：
- 后续待验证问题：
```

## 4. 综合证据并验证方案

把观察到的行为与解释分开记录，避免把个人判断写成用户事实。

| 观察事实 | 可能解释 | 证据强度 | 下一步验证 |
|----------|----------|----------|------------|
| 受访者每周导出表格再手工核对 | 当前系统无法支持跨来源比对 | 中 | 查看更多用户的实际操作记录 |

按风险选择验证方式：

- **问题验证**：确认目标用户是否反复遇到问题，以及影响是否足够大。
- **概念测试**：用简短方案描述或原型检查理解度，不把好评当成购买意愿。
- **可用性测试**：给出具体任务，观察是否能独立完成及卡点。
- **行为实验**：在可控范围内测试真实点击、申请、预约或付费行为。
- **技术验证**：用代表性数据验证质量、延迟、稳定性与成本约束。

实验开始前写清楚样本、周期、成功阈值、护栏指标和停止条件。若实验只验证兴趣表达，就不要据此推断实际留存或营收。

## 5. 做出决策并沉淀

研究结论至少应包含：

1. 我们研究了谁，以及哪些用户不在样本中。
2. 最重要的行为证据和反例是什么。
3. 哪些假设得到支持、被推翻或仍不确定。
4. 对产品决策有什么影响，哪些问题需要继续验证。
5. 结论的适用范围、日期及证据来源。

不要只保存访谈逐字稿。把结论关联到决策和后续指标，避免研究材料成为无人使用的档案。
