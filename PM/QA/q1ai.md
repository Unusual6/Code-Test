1. 模型选型

我会从业务需求出发，不是单纯比较模型排行榜，而是在明确业务成功标准的前提下，通过真实场景评测，找到满足效果要求、同时符合成本、延迟和可靠性约束的方案

第一，明确任务类型和质量要求。例如，是普通的意图识别、结构化信息提取，还是复杂的任务规划、工具调用。不同任务对模型的推理能力、指令遵循能力和结构化输出能力要求不同。

第二，建立评估标准。除了任务准确率，还要关注工具调用成功率、复杂任务的端到端完成率、响应延迟、单次任务成本，以及输出的稳定性。对于涉及外部设备执行的 Agent，还需要重点评估错误参数、错误工具调用和异常情况下的处理能力。

第三，使用真实业务样本进行对比测试。我会从实际任务中整理具有代表性的测试集，覆盖常规任务、复杂任务和异常场景，在尽量一致的提示词、工具定义和测试条件下，对候选模型进行评估，避免只看几个 Demo 就做决策。

第四，根据业务约束确定方案。如果复杂任务的完成率是核心指标，可以优先保证效果；如果任务量大、调用频繁，就需要更加关注推理成本和延迟。必要时采用分层策略，让简单任务使用成本更低的模型，复杂任务再调用能力更强的模型。

最终，我关注的不是哪个模型的综合能力最强，而是哪个模型在目标业务场景下，能够以可接受的成本和延迟，稳定地完成任务。

2. 选型具体会看哪些指标？效果怎么评估

不要只说准确率。可以按三层回答：
- 任务效果： 任务完成率、工具调用成功率、参数正确率、结果准确性。
- 使用体验： 响应延迟、任务执行耗时、失败后的恢复能力。
- 商业成本： 单次任务成本、Token 消耗、重试率，以及人工介入成本。
对 Agent 产品，尤其要区分模型本身的能力与整个系统的表现。模型输出正确，不代表工具调用和最终任务一定成功。

我会建立覆盖真实业务分布的测试集，先定义任务成功标准，再比较候选模型的表现。对于可自动判断的结果，使用规则或程序评估；对于复杂输出，可以结合人工盲评和明确的评分标准。上线后继续监控真实任务的成功率、失败类型和成本，避免离线测试结果与真实使用效果脱节。

3. 两个模型，一个效果好但贵，一个便宜但效果差，你怎么选？开源闭源怎么选？

先看效果差距是否影响核心业务指标。如果便宜模型只是在少数复杂任务上表现较差，可以考虑路由策略或失败升级机制；如果它会显著增加任务失败、重试和人工处理成本，那么表面上的低推理成本未必意味着更低的总成本。核心是比较单位成功任务的总成本，而不只是单次 API 调用价格

先验证两类模型是否都能满足任务质量要求，再比较综合成本、部署方式、数据安全、可控性、并发能力和维护成本。开源模型不一定更便宜，因为还需要考虑 GPU、推理服务和运维成本；闭源模型也不一定更好，要看实际任务表现及其服务约束。


4. 最终选型的原因分析
为了保证平台数据的安全性，再结合我们有大量计算资源。我们优先考虑闭源模型，我们之前使用过 GLM 和 GPT-oss-20B，后续最终选定了 DPS V4。

主要考虑的是我们的业务场景。这个 Agent 平台不是单纯的对话产品，而是需要理解用户的实验目标、组织执行流程，并通过工具调用外部设备和系统。因此，模型不仅要理解任务，还需要稳定地输出符合要求的调用参数和结构化内容。

在实际开发和任务执行过程中，我们会关注模型的输出稳定性、格式正确性和参数错误情况。相比只看模型能不能完成某次任务，我们更关注它能否持续、可靠地支撑整个执行链路。基于实际使用和开发验证的体验，DPS V4 在输出稳定性和格式、参数错误方面更符合我们的需求，因此最终选择了它。

不过，这个结论主要来自实际开发和任务运行中的验证，并不是在统一测试集上进行的严格量化对比，所以我不会直接声称它在所有指标上都优于 GLM 或 GPT-oss-20B。对于需要操作外部设备的场景，我们也不会完全依赖模型本身，而是通过参数校验、人工确认和执行中断等机制进一步控制风险。

主要体现在结构化输出和工具调用相关的环节。我们的 Agent 需要生成符合约定格式的内容，并传递工具调用所需的参数。如果格式不符合预期，或者参数出现错误，就可能导致后续工具调用失败，任务耗时增加，执行可靠性受到影响
