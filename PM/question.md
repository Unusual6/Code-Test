## 问题 1：项目背景与价值判断

**面试官提问**  
你如何判断「这个问题值得用 Agent 来解决」而非继续用传统工作流？你定义的核心用户价值和成功标准是什么？

**回答**  

**判断依据**：
1. **任务高度非标准化**：科研人员的需求差异大（同是「参数扫描实验」，因人/材料/设备组合不同），传统固定工作流覆盖率低，每次需人工改配置，成本高且易出错
2. **新需求响应慢**：已有脚本只能解决「已知标准流程」，而用户真正需要的是「用自然语言描述目标后，系统能自己拆解并执行」
3. **完全自主存在风险**：设备误操作、计算资源浪费等问题，必须保留人工确认节点

因此我设计了「Agent 自主决策 + 人工确认 + 工作流固化」的三层架构，通用模板可固化为标准工作流复用。

**核心用户价值**：将「从想法到可执行实验」的周期从小时/天级缩短到分钟级，同时将执行风险控制在可接受范围

**成功标准**（两层）：
- **过程标准**：一次请求能正确理解意图、合理拆解任务、关键节点人工确认后安全执行
- **结果标准**：最终输出被用户认可（或经追问补充后认可），整体任务成功率稳定在较高水平

**落地过程**：该判断基于前期用户访谈和痛点梳理，与业务、算法团队共同确认后推进

## 问题 2：0-1 产品设计与边界

**面试官提问**  
你如何定义 Agent 的功能边界？「自然语言路径」和「已有流程方案路径」的双路径设计基于什么考虑？如何决定哪些环节必须人工介入？

**回答**  

**功能边界**：仅开放已校准、可观测、可回滚的 Skill 和 MCP 能力，并通过 Harness 做黑名单动作限制，从源头控制风险

**双路径设计的核心考量**：「灵活性 vs 确定性」的平衡
- **自然语言路径**：用于新需求和探索性任务，发挥 Agent 自主拆解能力
- **已有流程路径**：用于高频、标准化任务，直接复用固化模板，降低不确定性和成本

**人工确认节点的划分原则**：「成本与不可逆性」
- **必须人工确认**：涉及真实设备动作、高成本计算资源、可能产生不可逆结果的操作
- **可直接执行**：纯生成类、低成本计算、结果可轻易重跑的任务

**边界迭代过程**：早期遇到过 Agent 对模糊指令过度自信导致误调设备的情况，后来才把「真实世界动作」全部上收为人工确认，并增加了确认前后的状态对比展示，提升用户信任

## 问题 3：技术理解与方案选型

**面试官提问**  
为什么选择 LangGraph 而不是 Dify、Coze 或自研状态机？遇到过哪些典型失败 case？产品侧如何设计兜底和可观测性？

**回答**  

**选择 LangGraph 的三点理由**：
1. **天然适配场景**：有向图 + 原生状态管理，适合「多步骤、有回环、需查询中间状态」的实验编排场景
2. **开发友好**：能暴露底层节点和状态，方便做精细的权限控制和调试，而 Dify/Coze 更偏低代码，灵活性不够
3. **成本平衡**：团队有一定工程能力，自研状态机成本高且长期维护负担重，LangGraph 是平衡点

**典型失败 case**：
- 工具重复调用（同一参数被多次执行）
- 设备状态回传延迟或丢失，导致后续节点基于错误状态继续执行
- 部分工具超时后 Agent 没有正确感知

**产品侧兜底设计**：
- 工具调用增加「次数上限 + 入参去重」校验
- 设备状态通过「回调 + 超时重试 + 最终人工确认」三重保障
- 每个关键节点都有可观测日志和状态快照，支持任务复盘和问题定位

这些机制是在前期几轮真实失败后，我推动产品侧补齐的

## 问题 4：可控性与评测体系

**面试官提问**  
Agent 成功率约 95%。你如何定义和拆解「成功率」？失败的 5% 主要分布在哪些环节？建立了怎样的评测集或线上监控机制？人工接管率、工具调用准确率、任务完成时长有跟踪吗？

**回答**  

**成功率定义**：从用户发起请求到最终返回结果的全链路中，任务被正确理解、合理拆解、安全执行，且最终输出符合用户预期（或经追问补充后符合）

**三个子指标拆解**：
- 意图理解准确率
- 任务拆解完整率
- 执行结果符合率

**失败分布（约 5%）**：
- **主要**：单次请求任务链路过长，上下文压缩后关键信息丢失，导致拆解遗漏或顺序错误
- **次要**：模糊指令下 Agent 过度自信，跳过了本该确认的节点
- **个别**：工具/设备状态异常未被及时感知

**评测与监控机制**：
- **离线评测集**：覆盖标准流程 + 大量 corner case（长链路、模糊指令、异常状态等），每次版本迭代必跑
- **线上监控**：实时跟踪成功率、人工接管率、工具调用准确率、任务完成时长，并按失败类型分类告警

这些指标和评测集是我主导定义并推动落地的，用于指导后续的上下文管理优化和拆解策略迭代

## 问题 5：智能优化能力产品化

**面试官提问**  
你把贝叶斯优化（BO）接入了 Agent 流程，实现了优化轮次减半、产率提升超过 5%。用户如何触发和使用这个优化能力？优化过程对用户是否透明？如何平衡「自动寻优」和「用户对结果的可控/可解释」需求？

**回答**  

**产品化设计**：贝叶斯优化能力被设计成一个可选的 Skill，用户在创建或编辑任务时，如果系统检测到该任务具备「可优化参数 + 历史数据」，会主动提示「是否开启智能参数寻优」。用户确认后，Agent 会在执行流程中自动插入优化循环

**两种使用模式**：
- **全自动**：系统按设定的轮次和目标自动寻优，结束后返回最优参数及对应结果
- **半自动**：每轮优化后暂停，展示当前最优、参数变化趋势和建议，由用户决定是否继续或采纳

**平衡「自动」和「可控/可解释」的三个设计**：
1. **过程完全可视化**：参数搜索轨迹、每轮产率变化
2. **用户可随时干预**：中断、修改约束条件或直接指定参数
3. **结果对比与解释**：对比「经验基线 vs 优化结果」，并给出简要解释

**迭代过程**：早期纯自动模式反馈「黑盒感强、不敢用」，我推动增加透明与干预能力，既保留了效率提升，又提升了用户信任

## 问题 6：个人贡献与决策

**面试官提问**  
这个项目是与中科院团队联合推进的。你个人主导或深度参与的决策有哪些？举 1-2 个例子说明当时面临什么分歧或不确定性，你如何推动最终方案落地？你和算法、工程同学协作时最常出现的冲突点是什么，怎么处理的？

**回答**  

**个人主导的两类决策**：
1. 需求抽象与优先级排序——剔除伪需求，凝练关键核心需求
2. 关键可控节点的设计

**具体例子**：早期中科院侧提出了很多「希望 Agent 能自动处理所有异常并继续执行」的需求。我通过实际用户操作日志和失败 case 分析后发现，真正高频且影响体验的是「任务拆解不清」和「高成本动作误触发」，而不是全面自动化。

**推动过程**：我推动把「真实设备动作和昂贵计算」全部上收为人工确认，并砍掉了部分低价值的全自动异常处理需求。当时算法和工程同学认为这会降低 Agent 的「智能感」，我用失败 case 占比数据和用户访谈反馈说服了大家。

**结果**：最终方案落地后，误操作投诉明显下降，用户信任度提升

**冲突处理方式**：
- 先站在对方立场理解资源约束
- 再用线上数据（失败率、用户反馈、使用频率）量化该需求对核心体验的影响
- 把讨论从「我觉得重要」变成「数据证明影响多大」
- 再共同决策

## 问题 7：算法背景如何赋能产品

**面试官提问**  
你有一年算法实习经历（模型蒸馏、自动标注工具等）。算法背景在你做产品时带来了哪些直接帮助？有没有因为懂技术而做出过和纯业务产品经理不一样的决策或判断？转型后你发现自己在产品思维上最大的短板是什么，目前如何弥补？

**回答**  

**算法背景带来的三点直接帮助**：
1. **判断能力边界**：能较快判断一个需求落在模型能力边界内还是外，从而更合理排优先级，避免把「当前模型做不到」的需求排进高优
2. **降低沟通成本**：和算法、工程沟通时能用同一套语言，减少「产品提需求 → 技术说做不到 → 反复拉扯」的成本
3. **评测与兜底设计**：在设计评测和兜底时更有体感，知道哪些地方容易出幻觉或状态不一致

**具体不同决策的例子**：早期有人提出「让 Agent 完全自动决定是否调用昂贵计算资源」。纯业务视角可能觉得「越自动越好」，但我清楚模型在模糊指令下容易过度自信，最终推动增加了「高成本动作强制人工确认 + 预估成本展示」。虽然牺牲了一点流畅度，但大幅降低了资源浪费和误操作风险

**转型后的产品思维短板**：早期为了赶进度，对需求砍得偏狠，后来发现有些当时觉得「伪」的需求其实影响用户信任和复购

**弥补方式**：需求评审时强制增加「用户真实使用路径验证」和「不做的后果量化」，不再只靠自己的判断快速砍需求

## 问题 8：商业化与下一步规划

**面试官提问**  
目前项目处于能力验证与产品化打磨阶段，尚未正式商业化。请谈谈你对这个平台后续商业化路径的思考：目标客户是谁？可能的收费模式是什么？从「试点验证」到「可规模化复制」还缺哪些关键能力或数据？如果让你重新规划，你会在 0-1 阶段更早做什么来为商业化铺路？

**回答**  

**当前阶段**：项目仍处于能力验证与产品化打磨阶段，商业化尚未正式启动，但路径已有初步思考

**目标客户**：高校实验室、科研院所以及有实验自动化需求的企业研发部门

**可能的收费模式**：
- **平台使用费**：按请求次数/Token 消耗计费，配合每月免费额度降低试用门槛
- **资源消耗费**：机时、样品、试剂等按实际使用结算
- **生态分成**：提供设备闲置时间的机构可获得一定比例分成，激励更多设备接入

**从试点到规模化复制，目前还缺**：
1. 更多样化的真实机构数据和长周期使用反馈
2. 可快速复制的标准接入模板和行业最佳实践
3. 清晰的 ROI 证明材料（帮用户节省了多少时间/成本）

**如果重新做 0-1，我会更早做两件事**：
1. 在试点阶段就强制收集「使用前后效率对比」数据
2. 优先打磨 2-3 个高频通用场景的完整闭环，形成可演示、可复制的标杆案例，而不是过早铺太多长尾能力

## 问题 9：通用性 vs 垂直场景

**面试官提问**  
你的项目落地在科学计算/实验自动化场景。如果今天让你把这套 Agent 能力抽象成更通用的平台（面向其他行业），你会保留哪些核心能力、抽象掉哪些领域特异性？你如何说服面试官「你不是只能做 AI4S 垂直场景的产品」？

**回答**  

这套 Agent 的核心能力是「自主决策」并「安全兜底不越界」。

**保留的核心能力**：
1. 自然语言任务理解与多步骤拆解
2. 基于状态的工作流编排与工具/设备调用
3. 关键节点的人工确认与风险兜底机制
4. 执行过程可观测、可中断、可复盘
5. 可选的智能优化（参数寻优）能力

**需要抽象掉的领域特异性**：具体的实验设备协议、生化领域的参数含义、特定试剂/样品的业务规则等，这些下沉为可插拔的 Skill 或行业插件

**说服点**：我做的不是「生化实验专用工具」，而是「复杂任务的可控自动化执行引擎」。科学计算场景只是验证场，因为它天然具备「流程长、工具多、成本高、需要强可控」的特点，这些特点在工业质检、供应链调度、企业流程自动化等场景同样存在。我已经验证了这套「自主+可控」架构能跑通，迁移到其他行业主要是行业 Know-how 和工具接入的问题，而不是底层产品能力的问题

## 问题 10：行业认知与自我定位

**面试官提问**  
当前 AI Agent 产品已经从「能跑 Demo」进入「要可控、要结果、要规模化」的阶段。结合你的一年产品经验，你认为目前市面上大多数 Agent 产品最大的问题是什么？你个人更想往「平台型 Agent 产品」还是「垂直场景 Agent 解决方案」方向深入？为什么？

**回答**  

**对行业问题的判断**：我认为目前大多数 Agent 产品最大的问题不是「不够聪明」，而是「不够可控、不够可验证、不够能规模化」。很多产品能跑通 Demo，但上线后失败不可解释、人工接管率高、无法证明稳定业务价值，最终停在试点阶段。真正难的是把 Agent 从「能做」变成「敢用、能复用、能持续产生结果」

**个人倾向**：更倾向平台型 Agent 产品方向

**三点理由**：
1. **核心能力可复用**：我过去一年验证的核心能力（任务拆解、工具调用、人工兜底、状态可观测）本身就具备跨场景复用潜力
2. **长期价值更高**：平台型能沉淀通用的编排、评测、权限、优化能力，也更匹配我「既懂技术边界又做产品」的背景
3. **成长空间更大**：垂直解决方案虽然落地快，但容易陷入重复造轮子，而平台型可以支撑多个垂直场景

**补充说明**：平台也需要通过垂直场景打磨，所以我不会排斥垂直，而是以平台能力为核心，用垂直场景验证和反哺
