### 1. 项目背景与价值判断
 
你主导的 Agent 任务自动化平台是面向科学计算/实验自动化场景的。请具体讲讲，你当时是如何判断「这个问题值得用 Agent 来解决」，而不是继续用传统工作流或脚本？你定义的核心用户价值和成功标准是什么？

**你的回答**  
对于复杂场景和多样的用户需求，固定的工作流或基于规则的定式脚本，很难全部正确且合理的满足需求，所以通过agent自主决策编排工作流，并通过人工确认编排的合理性，若为通用模板可以保存固化成标准工作流。这是一套agent自主决策加人工兜底和工作流固化模板的架构。用户价值我定义的是，智能体能够清晰的理解用户的请求，需求拆分，并能够安全执行通过。成功标准是，用户一次请求可以实现最终用户满意的结果输出，若请求不清晰，则对用户追问补充。

**得分：6.5 / 10**

**分析**  
- 优点：点出了「固定工作流无法覆盖多样需求」这个核心痛点，提出了「Agent自主 + 人工确认 + 固化模板」的架构，方向正确。  
- 不足：判断依据偏笼统，缺少具体场景例子和量化痛点（例如原来配置一个流程要多久、失败率多高、用户投诉点是什么）。用户价值和成功标准定义偏功能性（理解、拆分、执行），缺少业务结果导向（效率提升、人力节省、实验成功率等）。个人如何推动这个判断落地的过程几乎没有。

**高分参考回答（建议替换）**  
当时判断值得用 Agent，主要基于三个观察：  
1. 用户（科研人员）的任务高度非标准化，同样是「做一组参数扫描实验」，不同人、不同材料、不同设备组合差异很大，传统固定工作流覆盖率低，每次都要人工改配置，成本高且容易出错。  
2. 已有脚本/工作流只能解决「已知标准流程」，对新需求响应慢，而用户真正需要的是「用自然语言描述目标后，系统能自己拆解并执行」。  
3. 完全自主又存在风险（设备误操作、计算资源浪费），所以必须保留人工确认节点。  

核心用户价值我定义为：**把「从想法到可执行实验」的周期，从小时/天级缩短到分钟级，同时把执行风险控制在可接受范围**。  
成功标准有两层：  
- 过程标准：一次请求能正确理解意图、合理拆解任务、关键节点人工确认后安全执行。  
- 结果标准：最终输出结果被用户认可（或通过追问补充后认可），且整体任务成功率稳定在较高水平。  
这个判断是我在前期用户访谈和痛点梳理后，与业务、算法共同确认的。

### 2. 0-1 产品设计与边界
 
在从0到1的过程中，你是如何定义 Agent 的功能边界的？特别是「自然语言路径」和「已有流程方案路径」的双路径设计，以及关键人工确认节点，你当时是基于什么考虑决定哪些环节必须人工介入、哪些可以完全交给 Agent？

**你的回答**  
功能边界是开放给agent已经核对校准过的skill或mcp功能，就在已有的功能范围内自主执行，并通过harness限定黑名单动作对其进行动作兜底。双路线是既给定agent自主灵活性又提供安全固化流程。涉及到任务操作机器的实际动作或者调用计算资源展开实验等需要一定成本代价的请求，需要人工确认核实，避免误操作。其余的生成任务或一些低成本的计算任务可直接执行。

**得分：7 / 10**

**分析**  
- 优点：边界定义清晰（已校准的 Skill/MCP + 黑名单兜底），双路径逻辑和「高成本动作必须人工确认」的原则是对的，体现了风险意识。  
- 不足：缺少「为什么这样划分」的决策过程和个人判断。黑名单/白名单具体怎么定的？早期有没有踩过坑导致边界调整？双路径的优先级或默认策略是什么？这些细节能体现产品深度。

**高分参考回答（建议替换）**  
功能边界我定义为「只开放已校准、可观测、可回滚的 Skill 和 MCP 能力」，并通过 Harness 做黑名单动作限制，从源头控制风险。  

双路径设计的核心考量是「灵活性 vs 确定性」的平衡：  
- 自然语言路径：给新需求和探索性任务用，发挥 Agent 自主拆解能力。  
- 已有流程路径：给高频、标准化任务用，直接复用固化模板，降低不确定性和成本。  

人工确认节点的划分原则是「成本与不可逆性」：  
- 必须人工确认：涉及真实设备动作、高成本计算资源、可能产生不可逆结果的操作。  
- 可直接执行：纯生成类、低成本计算、结果可轻易重跑的任务。  

这个边界不是一开始就定死的，早期我们遇到过 Agent 对模糊指令过度自信导致误调设备的情况，后来才把「真实世界动作」全部上收为人工确认，并增加了确认前后的状态对比展示，提升用户信任。

### 3. 技术理解与方案选型
 
你用了 LangGraph 做编排，同时结合了 RAG、MCP Server、MQTT 设备对接。请说明为什么选择 LangGraph 而不是其他框架（如 Dify、Coze、自研状态机）？在工具调用和设备状态回传这块，你遇到过哪些典型的失败 case，产品侧是如何设计兜底和可观测性的？

**你的回答**  
选型用langraph是因为其有向图结构和状态保持，自然适配状态查询和工作流编排调度设计，且更适合开发人员的工具暴露底层代码接口。失败case遇到工具重复执行，产品测会限定工具调用次数和多次调用之前的入参是否相同来判断是重复调用。设备状态回传，会通过回调函数来兜底，保证流转节点的安全响应更新。

**得分：6 / 10**

**分析**  
- 优点：选型理由（有向图 + 状态保持 + 底层可控）基本正确，提到了重复调用和回调兜底。  
- 不足：对比其他方案不够充分（为什么不选 Dify/Coze？自研状态机的取舍是什么？），失败 case 只举了一个，兜底和可观测性描述偏技术实现，缺少产品侧的完整设计（用户如何感知失败、如何介入、如何复盘）。

**高分参考回答（建议替换）**  
选择 LangGraph 主要基于三点：  
1. 有向图 + 原生状态管理，天然适合「多步骤、有回环、需查询中间状态」的实验编排场景。  
2. 对开发更友好，能暴露底层节点和状态，方便我们做精细的权限控制和调试，而 Dify/Coze 更偏低代码，灵活性不够。  
3. 当时团队有一定工程能力，自研状态机成本高且长期维护负担重，LangGraph 是平衡点。  

典型失败 case 包括：  
- 工具重复调用（同一参数被多次执行）。  
- 设备状态回传延迟或丢失，导致后续节点基于错误状态继续执行。  
- 部分工具超时后 Agent 没有正确感知。  

产品侧兜底设计：  
- 工具调用增加「次数上限 + 入参去重」校验。  
- 设备状态通过回调 + 超时重试 + 最终人工确认三重保障。  
- 每个关键节点都有可观测日志和状态快照，支持任务复盘和问题定位。  
这些机制是在前期几轮真实失败后，我推动产品侧补齐的。

### 4. 可控性与评测体系
 
Agent 成功率约95%。请详细讲讲你是如何定义和拆解「成功率」这个指标的？失败的5%主要分布在哪些环节？你建立了怎样的评测集或线上监控机制来持续发现和优化问题？人工接管率、工具调用准确率、任务完成时长这些指标你有跟踪吗？

**你的回答**  
成功率是通过用户请求埋点到最终实验结束返回结果。能够正确解析执行任务，并并按照用户请求返回结果，就是成功。失败主要分布在，一次请求任务过多，智能体上下文过长导致任务拆解不清晰，会漏掉或者错误执行，导致最终的反馈结果不正确。我建立评测集包含，标准的执行流程和大量的corner case请求。这三个指标都有跟踪。

**得分：6.5 / 10**

**分析**  
- 优点：成功率定义基本清楚，失败原因指向「任务过多导致上下文过长、拆解不清」，评测集提到了标准流程 + corner case，三个指标都有跟踪。  
- 不足：拆解不够细（成功率是否区分「理解正确但执行失败」和「理解就错了」？），失败分布缺少量化占比，评测集和线上监控的具体机制、迭代动作没有展开，个人如何推动指标建设的过程缺失。

**高分参考回答（建议替换）**  
成功率我定义为：从用户发起请求到最终返回结果的全链路中，任务被正确理解、合理拆解、安全执行，且最终输出符合用户预期（或经追问补充后符合）。  

进一步拆成三个子指标：  
- 意图理解准确率  
- 任务拆解完整率  
- 执行结果符合率  

失败的约5%主要集中在：  
- 单次请求任务链路过长，上下文压缩后关键信息丢失，导致拆解遗漏或顺序错误（占比最高）。  
- 模糊指令下 Agent 过度自信，跳过了本该确认的节点。  
- 个别工具/设备状态异常未被及时感知。  

评测与监控机制：  
- 离线评测集：覆盖标准流程 + 大量 corner case（长链路、模糊指令、异常状态等），每次版本迭代必跑。  
- 线上监控：实时跟踪成功率、人工接管率、工具调用准确率、任务完成时长，并按失败类型分类告警。  
这些指标和评测集是我主导定义并推动落地的，用于指导后续的上下文管理优化和拆解策略迭代。

### 5. 智能优化能力产品化
 
你把贝叶斯优化（BO）接入了 Agent 流程，并实现了优化轮次减半、产率提升超过5%。请从产品角度讲讲：用户是如何触发和使用这个优化能力的？优化过程对用户是否透明？你如何平衡「自动寻优」和「用户对结果的可控/可解释」需求？

**你的回答**  
该能力是以skill的形式部署的，用户可在原有任务中选配增加该skill，前提是有一定的数据积累和可优化项。

**得分：4.5 / 10**

**分析**  
- 优点：触发方式（作为 Skill 选配）和前提条件（有数据积累）说清楚了。  
- 不足：回答过短，几乎没有展开「如何使用」「过程是否透明」「如何平衡自动与可控」。这是最能体现产品sense的一题，目前信息量严重不足，面试官会认为你只是把算法能力「挂」了上去，而没有真正做产品化设计。

**高分参考回答（建议替换）**  
贝叶斯优化能力被我设计成一个可选的 Skill，用户在创建或编辑任务时，如果系统检测到该任务具备「可优化参数 + 历史数据」，会主动提示「是否开启智能参数寻优」。用户确认后，Agent 会在执行流程中自动插入优化循环。  

使用上支持两种模式：  
- 全自动：系统按设定的轮次和目标自动寻优，结束后返回最优参数及对应结果。  
- 半自动：每轮优化后暂停，展示当前最优、参数变化趋势和建议，由用户决定是否继续或采纳。  

为了平衡「自动」和「可控/可解释」：  
1. 优化过程完全可视化（参数搜索轨迹、每轮产率变化）。  
2. 用户可随时中断、修改约束条件或直接指定参数。  
3. 最终结果会对比「经验基线 vs 优化结果」，并给出简要解释。  

这个设计是在早期纯自动模式反馈「黑盒感强、不敢用」后，我推动增加的透明与干预能力，既保留了效率提升，又提升了用户信任。
