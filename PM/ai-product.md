# AI 产品管理

> 目标：把模型能力转化为可靠、可衡量且值得用户使用的产品结果。

## 1. 先判断是否需要 AI

先定义用户任务和成功结果，再比较实现方式。若规则、搜索或传统自动化能以更低成本、更高稳定性解决问题，不必为了使用 AI 而引入模型。

| 评估项 | 需要回答的问题 |
|--------|----------------|
| 用户价值 | AI 是否改善任务质量、完成时间或可访问性？ |
| 任务性质 | 输入是否模糊、多样或需要语言/感知能力？ |
| 可验证性 | 什么结果算正确？是否有权威答案或可接受范围？ |
| 容错空间 | 错误的影响是什么？用户能否检查、修改或撤销？ |
| 数据条件 | 输入数据是否可用、合法、代表真实场景且质量足够？ |
| 经济性 | 模型调用、检索、审核、支持和人工复核的总成本是否可接受？ |
| 替代方案 | 规则、搜索、人工流程或混合方案是否更合适？ |

## 2. 定义系统边界与体验

明确 AI 在产品中的职责，不把模型输出包装成确定事实。

- **输入边界**：支持什么输入，如何处理缺失、歧义、超长或不可信内容。
- **输出边界**：输出格式、长度、语气、引用来源和禁止内容。
- **不确定性**：何时追问、拒答、展示置信提示或转人工。
- **用户控制**：允许修改、重试、撤销、反馈和查看依据。
- **失败体验**：超时、限流、无结果、工具失败或模型不可用时，明确告知并提供可行下一步。
- **责任边界**：在医疗、金融、法律等高影响场景，设置适当审查、限制和专业人员参与。

不要仅用“模型有幻觉”解释产品问题。通过来源展示、约束输出、验证机制和交互设计降低错误进入用户决策的概率。

## 3. 建立评估集

评估集应来自真实任务分布，并覆盖正常、困难和高风险情况。不要只挑模型容易答对的样例。

| 样例类别 | 示例关注点 |
|----------|------------|
| 常见输入 | 主流用户任务是否完成 |
| 边界输入 | 缺字段、格式异常、超长内容 |
| 歧义输入 | 是否追问而非擅自假设 |
| 无依据问题 | 是否承认不知道或拒绝回答 |
| 对抗与越权输入 | 是否遵循产品规则和数据访问边界 |
| 不同群体/语言 | 是否存在明显质量差异 |
| 真实失败样例 | 是否避免已知错误模式 |

每个样例记录输入、期望行为、可接受范围、严重错误定义和版本。确定性指标可自动计算；开放式输出应结合人工评审或经校准的评审方法，并定期抽查评审一致性。

### 评估方案模板

```markdown
## 评估：[功能/版本]
- 用户任务与预期价值：
- 数据来源、授权与脱敏方式：
- 样本分层及数量：
- 质量指标与通过阈值：
- 高严重度错误及容忍度：
- 延迟、成本与稳定性阈值：
- 基线方案：
- 评估结果与失败案例：
- 上线 / 调整 / 停止决定：
```

## 4. 设计线上指标

线上指标需要同时衡量用户结果、质量、系统表现和成本，不能只看调用量或单一模型分数。

| 维度 | 指标示例 |
|------|----------|
| 用户结果 | 任务完成率、完成耗时、结果采纳率、返工率 |
| 质量 | 事实错误率、无依据回答率、任务评审通过率 |
| 体验 | 首 token 延迟、完整响应延迟、重试率、放弃率 |
| 稳定性 | 超时率、错误率、依赖服务可用性 |
| 成本 | 单次成功任务成本、每活跃用户成本、人工复核成本 |
| 风险 | 隐私事件、有害输出率、越权访问率、投诉率 |

指标定义应包含分母、统计窗口、去重规则、分群方式和数据延迟。结果指标需要护栏指标配套，避免通过降低质量或增加用户操作来虚增转化。

## 5. 选择合适的架构策略

- **提示词调整**：适用于任务定义清晰、知识不常变化且不需要外部事实的场景。
- **检索增强生成**：适用于回答需要依据私有或持续更新的知识；同时评估检索召回、来源质量和引用正确性。
- **工具调用**：适用于需要查询或执行外部动作的任务；对有副作用的操作增加权限检查、确认和审计。
- **微调**：适用于行为模式稳定、样例充足且提示词等方案无法经济满足要求的场景；先核实数据质量和维护成本。
- **混合流程**：将规则、模型、检索和人工审核组合，按风险把任务路由到合适路径。

架构选择以端到端任务表现为准。单独提升模型基准分数，不一定改善实际用户结果。

## 6. 管理数据与上线风险

- 盘点输入、输出、日志和反馈中包含的个人或敏感信息，遵循最小收集和最短留存原则。
- 确认数据来源、使用权限、保留期限、删除流程和跨境要求。
- 把用户输入和检索内容视为不可信数据，避免其覆盖系统规则或触发未授权工具操作。
- 对外部工具实施最小权限，校验参数，限制可执行动作并记录审计信息。
- 通过灰度发布观察分群质量、成本和护栏指标；设置暂停与回滚条件。
- 建立高严重度错误的报告、分级、处置和复盘流程。

## 7. 持续迭代

上线后把真实失败样例纳入评估集，确认修复没有损害其他场景。模型、提示词、检索数据、工具和产品流程变化都可能改变行为，因此应记录版本并在关键变更后重新评估。

每轮迭代明确一个主要问题、预期指标变化、验证周期和停止条件。若用户结果没有改善，应重新检查任务设计、数据、流程和替代方案，而不只是继续更换模型。
