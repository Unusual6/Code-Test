# AI 产品管理

> 目标：把模型能力转化为可靠、可衡量且值得用户使用的产品结果。

## 1. 先判断是否需要 AI

先定义用户任务和成功结果，再比较实现方式。若规则、搜索或传统自动化能以更低成本、更高稳定性解决问题，不必为了使用 AI 而引入模型。

| 评估项 | 需要回答的问题 |
|--------|----------------|
| 用户价值 | AI 是否改善任务质量、完成时间或可访问性？ |
| 任务性质 | 输入是否模糊、多样或需要语言/感知能力？ |
| 可验证性 | 什么结果算正确？是否有权威答案或可接受范围？ |
| 容错空间 | 错误的影响是什么？用户能否检查、修改或撤销？ |
| 数据条件 | 输入数据是否可用、合法、代表真实场景且质量足够？ |
| 经济性 | 模型调用、检索、审核、支持和人工复核的总成本是否可接受？ |
| 替代方案 | 规则、搜索、人工流程或混合方案是否更合适？ |

## 2. 定义系统边界与体验

明确 AI 在产品中的职责，不把模型输出包装成确定事实。

- **输入边界**：支持什么输入，如何处理缺失、歧义、超长或不可信内容。
- **输出边界**：输出格式、长度、语气、引用来源和禁止内容。
- **不确定性**：何时追问、拒答、展示置信提示或转人工。
- **用户控制**：允许修改、重试、撤销、反馈和查看依据。
- **失败体验**：超时、限流、无结果、工具失败或模型不可用时，明确告知并提供可行下一步。
- **责任边界**：在医疗、金融、法律等高影响场景，设置适当审查、限制和专业人员参与。

不要仅用"模型有幻觉"解释产品问题。通过来源展示、约束输出、验证机制和交互设计降低错误进入用户决策的概率。

## 3. AI 能力图谱与产品模式

PM 需要快速判断用户任务属于哪类 AI 能力，从而选择合适的技术方案和评估标准。

| 能力类别 | 典型任务 | 产品形态举例 | 关键评估维度 |
|----------|----------|-------------|-------------|
| 文本生成 | 写作、摘要、翻译、改写 | Copilot、写作助手 | 流畅度、忠实度、风格一致性 |
| 信息提取 | 实体识别、字段抽取、结构化 | 表单自动填充、简历解析 | 准确率、召回率、格式正确率 |
| 分类与审核 | 标签分类、内容审核、意图识别 | 工单路由、评论过滤 | 精确率、召回率、误判代价 |
| 对话与推理 | 多轮对话、问答、规划 | 智能客服、Agent | 任务完成率、多轮连贯性、拒答准确率 |
| 推荐与排序 | 个性化推荐、搜索排序 | Feed 流、搜索结果 | 点击率、多样性、新颖性 |
| 语义检索 | 相似搜索、知识库问答 | RAG 系统、文档检索 | 召回率、MRR、答案忠实度 |
| 代码生成 | 补全、转换、解释、调试 | 编程助手 | 执行通过率、安全性、可维护性 |
| 多模态 | 图像理解、图文生成、语音识别 | 视觉助手、语音交互 | 跨模态一致性、延迟、准确率 |

对于 **Agent（智能体）** 场景——需要多步规划、工具编排或自主决策——产品设计应额外关注：

- **任务边界**：明确 Agent 能自主执行的动作范围，超出范围的请求必须转人工或拒绝。
- **工具设计**：每个工具的接口、参数约束、权限和副作用需要清晰定义。
- **人机协作**：关键动作前设置确认节点，让用户保持控制权。
- **错误恢复**：Agent 执行链中任一步骤失败时，需要回滚、重试或降级策略。
- **可观测性**：每一步决策和工具调用都应可追踪、可审计。
- **成本与延迟**：多步执行的成本和延迟会累积，需要设置上限和超时机制。

## 4. 用户引导与预期管理

AI 产品的落地障碍往往不是技术，而是用户不知道 AI 能做什么、会犯什么错。引导设计的核心是让用户在真实场景中快速获得一次成功体验，而非罗列功能列表。

- **首次使用引导**：用 2-3 个真实场景示例让用户立即完成一次成功任务，而非展示能力清单。
- **渐进式披露**：在用户完成基础任务后，适时提示进阶能力（如"你还可以让我帮你总结全文"），而非在帮助文档中一次性列出。
- **失败后的引导**：当 AI 输出不理想时，提供具体的改进建议（如"你可以补充 XX 信息，我会给出更准确的回答"），而非只说"出错了"。
- **能力变化沟通**：模型升级后行为可能变化（如更保守或更激进），需要主动告知用户并给适应期。
- **信任校准**：通过展示置信度、依据来源等方式，帮助用户建立对 AI 输出的合理信任——既不盲目采信，也不完全忽视。

## 5. 建立评估集

评估集应来自真实任务分布，并覆盖正常、困难和高风险情况。不要只挑模型容易答对的样例。

| 样例类别 | 示例关注点 |
|----------|------------|
| 常见输入 | 主流用户任务是否完成 |
| 边界输入 | 缺字段、格式异常、超长内容 |
| 歧义输入 | 是否追问而非擅自假设 |
| 无依据问题 | 是否承认不知道或拒绝回答 |
| 对抗与越权输入 | 是否遵循产品规则和数据访问边界 |
| 不同群体/语言 | 是否存在明显质量差异 |
| 真实失败样例 | 是否避免已知错误模式 |

每个样例记录输入、期望行为、可接受范围、严重错误定义和版本。确定性指标可自动计算；开放式输出应结合人工评审或经校准的评审方法，并定期抽查评审一致性。

### 评估方案模板

```markdown
## 评估：[功能/版本]
- 用户任务与预期价值：
- 数据来源、授权与脱敏方式：
- 样本分层及数量：
- 质量指标与通过阈值：
- 高严重度错误及容忍度：
- 延迟、成本与稳定性阈值：
- 基线方案：
- 评估结果与失败案例：
- 上线 / 调整 / 停止决定：
```

## 6. 设计线上指标

线上指标需要同时衡量用户结果、质量、系统表现和成本，不能只看调用量或单一模型分数。

| 维度 | 指标示例 |
|------|----------|
| 用户结果 | 任务完成率、完成耗时、结果采纳率、返工率 |
| 质量 | 事实错误率、无依据回答率、任务评审通过率 |
| 体验 | 首 token 延迟、完整响应延迟、重试率、放弃率 |
| 稳定性 | 超时率、错误率、依赖服务可用性 |
| 成本 | 单次成功任务成本、每活跃用户成本、人工复核成本 |
| 风险 | 隐私事件、有害输出率、越权访问率、投诉率 |

指标定义应包含分母、统计窗口、去重规则、分群方式和数据延迟。结果指标需要护栏指标配套，避免通过降低质量或增加用户操作来虚增转化。

## 7. 选择合适的架构策略

- **提示词调整**：适用于任务定义清晰、知识不常变化且不需要外部事实的场景。
- **检索增强生成（RAG）**：适用于回答需要依据私有或持续更新的知识；同时评估检索召回、来源质量和引用正确性。
- **工具调用**：适用于需要查询或执行外部动作的任务；对有副作用的操作增加权限检查、确认和审计。
- **微调**：适用于行为模式稳定、样例充足且提示词等方案无法经济满足要求的场景；先核实数据质量和维护成本。
- **混合流程**：将规则、模型、检索和人工审核组合，按风险把任务路由到合适路径。

架构选择以端到端任务表现为准。单独提升模型基准分数，不一定改善实际用户结果。

对于需要 **多步规划、工具编排或自主决策** 的场景，考虑 **Agent 模式**：

- 明确 Agent 的任务边界与可调用工具集，每个工具定义输入输出契约、权限和副作用。
- 设计人机协作节点：关键动作前需用户确认，高风险操作强制人工审核。
- 建立错误恢复机制：单步失败时重试、回滚或降级到人工，避免级联错误。
- 保证可观测性：每步决策、工具调用和中间结果应可追踪和审计。
- 控制成本与延迟：多步执行的成本和延迟会累积，设置单任务上限和超时机制。

对于 **流式输出** 与 **批量返回** 的选择：流式输出（逐 token 返回）可改善用户感知延迟，适合对话和长文本场景；批量返回适合需要完整结果后再展示的场景（如分类、提取）。实时对话与异步任务在架构选型上有本质差异，需明确区分。

## 8. 管理数据与上线风险

- 盘点输入、输出、日志和反馈中包含的个人或敏感信息，遵循最小收集和最短留存原则。
- 确认数据来源、使用权限、保留期限、删除流程和跨境要求。
- 把用户输入和检索内容视为不可信数据，避免其覆盖系统规则或触发未授权工具操作。
- 对外部工具实施最小权限，校验参数，限制可执行动作并记录审计信息。
- 通过灰度发布观察分群质量、成本和护栏指标；设置暂停与回滚条件。
- 建立高严重度错误的报告、分级、处置和复盘流程。

## 9. 反馈闭环与数据飞轮

AI 产品的核心竞争力往往在于“越用越好”。这需要建立从用户反馈到系统改进的闭环。

- **反馈采集设计**：区分隐式信号（采纳、修改、放弃、重复请求）和显式反馈（点赞、纠错、评价），前者量大但噪声高，后者精准但采集率低。
- **反馈回流路径**：明确反馈如何回流到评估集、提示词优化或微调数据，形成“发现问题 → 修复 → 验证”的闭环。
- **数据飞轮构建**：使用越多 → 数据越好 → 效果越好 → 使用越多。量化飞轮的每个环节，找到瓶颈。
- **冷启动策略**：上线初期优先积累核心场景的高质量数据，而非追求覆盖面；可用人工标注、合成数据或迁移学习启动。
- **反馈偏差监控**：上线后持续监控反馈分布，防止采样偏差（如只有不满用户才提交反馈）导致优化方向偏离。

## 10. 模型选型与供应商管理

模型选型不是单纯比较基准分数，而是综合评估产品适配度、成本结构和长期风险。

| 决策维度 | 自建/微调 | API 调用 | 开源部署 |
|----------|-----------|----------|----------|
| 初始投入 | 高（数据、算力、团队） | 低（快速验证） | 中（基础设施、运维） |
| 长期成本 | 边际成本低 | 随调用量线性增长 | 运维和升级成本 |
| 数据隐私 | 完全可控 | 依赖供应商协议 | 完全可控 |
| 定制灵活性 | 高 | 低（受限于接口） | 高 |
| 适用场景 | 有数据壁垒、长期投入 | 快速验证、非核心能力 | 合规要求高、需私有化 |

供应商评估维度：

- **能力匹配度**：在目标场景的实际表现，而非通用基准分数。
- **延迟与吞吐**：P50/P95/P99 延迟是否满足产品交互要求。
- **成本结构**：按 token、按次、按并发计费，估算不同用量下的月成本。
- **合规与数据归属**：数据是否用于训练、是否支持数据删除、是否符合行业合规。
- **供应商锁定风险**：切换成本、接口兼容性、是否有替代方案。

多供应商策略：避免单一供应商依赖，核心场景准备降级方案（如主用 A 模型，不可用时切 B 模型）。定期评估供应商的模型更新、定价变化和合规政策。

模型版本升级时：先在测试环境用评估集验证，确认关键指标无回退；对比新旧版本在真实流量样本上的表现；制定灰度切换方案，保留回退能力。

## 11. 持续迭代

上线后把真实失败样例纳入评估集，确认修复没有损害其他场景。模型、提示词、检索数据、工具和产品流程变化都可能改变行为，因此应记录版本并在关键变更后重新评估。

每轮迭代明确一个主要问题、预期指标变化、验证周期和停止条件。若用户结果没有改善，应重新检查任务设计、数据、流程和替代方案，而不只是继续更换模型。

迭代过程中应关注：

- **数据飞轮闭环**：把线上反馈持续回流到评估集和训练数据中，形成产品能力的正向循环。
- **模型版本管理**：记录每次模型、提示词、检索数据或工具的变更，建立变更日志，便于问题回溯。
- **A/B 测试框架**：关键变更通过 A/B 测试验证效果，避免全量上线后才发现回退。
- **评估集演化**：随着产品使用，持续补充新的失败样例和边界场景，保持评估集的时效性。
- **成本趋势监控**：随调用量增长和功能迭代，持续优化单次成功任务成本，确保商业可持续性。
