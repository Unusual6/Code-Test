# 产品交付与协作

> 目标：让团队对交付范围、决策、依赖和上线结果形成共同预期。

## 1. 从目标拆解交付范围

把产品目标拆成用户可完成的任务和可验收的结果，不直接从页面或技术模块开始列需求。

```text
业务/用户目标
  -> 用户任务
    -> 可验证结果
      -> 交付项与验收标准
```

每项交付内容至少说明：目标用户、触发条件、主流程、边界与异常、权限、数据记录、验收方式。明确不做的内容，控制范围蔓延。

### 范围清单

| 优先级 | 交付项 | 用户价值 | 验收条件 | 依赖 / 风险 |
|--------|--------|----------|----------|-------------|
| P0 | [必须交付] | [解决的任务] | [可观察、可复现的结果] | [依赖及负责人] |
| P1 | [重要但可延后] | [预期收益] | [验收条件] | [风险] |
| 不做 | [明确排除项] | [说明原因或替代方案] | - | - |

## 2. 建立可执行的验收标准

验收标准描述用户可观察的行为和系统结果，尽可能避免“体验良好”“支持正常使用”等主观表述。

```gherkin
场景：用户提交信息完整的申请
  假设：用户已登录且拥有提交权限
  当：用户提交所有必填字段
  那么：系统创建一条申请记录
  并且：用户能看到提交成功状态和后续处理入口
```

验收时覆盖：

- 主流程、空状态、加载状态、错误与重试。
- 权限不足、重复提交、边界值和并发情况。
- 数据是否正确保存、展示、统计和追踪。
- 关键性能、安全、隐私和兼容要求。
- AI 功能的拒答、低置信度、超时、人工修订与回退路径。

## 3. 管理依赖与变更

### 协作节奏

| 节点 | PM 准备 | 参与方 | 产出 |
|------|---------|--------|------|
| 需求澄清 | 目标、用户证据、范围和未知项 | 设计、研发、数据、业务 | 方案问题清单 |
| 方案评审 | 流程、原型、规则、验收条件 | 相关执行团队 | 决策与待办 |
| 开发同步 | 优先级、依赖、变更记录 | 研发、测试、设计 | 风险与阻塞项 |
| 上线评审 | 验收结果、监控、回滚方案 | 发布相关人员 | 上线决定 |
| 上线复盘 | 指标、反馈、事故和假设变化 | 产品团队及相关方 | 后续行动 |

评审的重点是尽早暴露决策和依赖，不是追求所有人对每个细节都达成一致。记录争议、决策人、结论和复查条件。

### 变更记录模板

```markdown
## 变更：[事项] / [日期]
- 原范围：
- 变更内容：
- 触发原因与证据：
- 对用户价值、进度、成本、风险的影响：
- 方案与被放弃的选项：
- 决策人 / 相关方：
- 后续行动与截止时间：
```

## 4. 发布准备

发布前确认：

- 核心路径通过验收，已知问题及影响范围明确。
- 埋点、看板、日志和告警可用于判断功能是否正常。
- 客服、运营、销售等需要支持的团队已获得变更信息。
- 权限、隐私、合规和安全事项已由对应责任人确认。
- 灰度范围、扩大条件、暂停条件和回滚方式明确。
- 对用户的提示、帮助内容和迁移安排已准备。

### 发布决策记录

```markdown
## 发布：[版本/功能]
- 发布目标与范围：
- 验收结果：
- 已知问题：
- 灰度对象与比例：
- 成功指标与观察周期：
- 护栏指标及阈值：
- 暂停 / 回滚条件：
- 监控负责人与值守安排：
- 决策人与时间：
```

## 5. 上线后复盘

复盘要判断结果与预期的差异，并形成行动，不以“按时上线”作为成功结论。

- **结果**：目标指标、护栏指标和用户反馈如何变化？
- **解释**：哪些因素可能造成变化？是否有证据区分相关性与因果性？
- **决策**：继续投入、调整、扩大、暂停还是下线？
- **行动**：负责人、完成时间和验证方式是什么？
- **学习**：原有假设哪些被证实或推翻，后续如何更新？

复盘问题聚焦流程和系统性因素，避免只归因于个人。高影响事项应设置后续检查日期，确认改进是否有效。
