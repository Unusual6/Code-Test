# 产品基本功

所有 PM 的底层能力，AI PM 同样必须具备。

---

## 1. 需求分析

> 核心目标：识别真实用户痛点，而不是照单全收业务需求。

### 1.1 需求收集方法

| 方法 | 适用场景 | 关键要点 |
|------|----------|----------|
| 用户访谈 | 探索阶段，挖掘深层动机 | 问"为什么"而非"你想要什么"；关注行为而非观点 |
| 数据分析 | 验证假设，量化问题 | 关注异常值、漏斗流失点、用户路径分叉 |
| 竞品分析 | 了解市场基线和差异化空间 | 不照搬功能，理解其背后的用户场景和取舍逻辑 |
| 一线反馈 | 发现真实痛点 | 客服工单、销售反馈、社区讨论、应用商店评论 |
| 场景观察 | 发现用户未意识到的需求 | 在真实环境中观察用户操作，记录"变通方案"（workaround） |

### 1.2 需求分析框架

**用户故事（User Story）**

```
作为 [角色]，我希望 [功能]，以便 [价值/目的]。
```

**Jobs to be Done (JTBD)**

- 用户"雇佣"产品来完成什么任务？
- 功能性任务 + 情感性任务 + 社会性任务

**需求层次判断**

| 层次 | 说明 | 示例 |
|------|------|------|
| 基本型需求 | 没有会不满，有了觉得理所当然 | 页面加载速度、基本功能可用 |
| 期望型需求 | 越多越好，直接关联满意度 | 搜索准确率、推荐相关性 |
| 兴奋型需求 | 没有不会不满，有了会惊喜 | 智能摘要、一键生成报告 |

### 1.3 识别真伪需求

**真需求的特征：**
- 有明确的用户场景和痛点
- 能衡量成功标准（行为变化或业务指标）
- 与产品愿景和战略方向一致

**伪需求的信号：**
- "老板说的" / "竞品有我们也要有"
- 无法描述具体谁在什么场景下需要
- 解决方案先于问题出现（"我要用区块链做 XX"）
- 用一句话说不清价值

### 1.4 AI PM 特别关注

- **数据需求**：AI 功能需要什么数据？数据从哪来？质量如何保证？
- **模型能力边界**：当前技术能做到什么程度？什么是"足够好"？
- **用户预期管理**：AI 不是万能的，需要设计合理的用户预期和降级方案。

## 2. 产品设计

> 核心目标：将需求转化为可落地的产品方案。

### 2.1 用户流程设计

**设计步骤：**

1. **明确核心任务**：用户使用产品的最主要目的是什么？
2. **绘制主流程**：最理想路径（Happy Path），步骤越少越好
3. **补充分支流程**：不同角色、不同场景的差异化路径
4. **设计异常流程**：出错、超时、数据缺失时的处理方式
5. **设计空状态**：首次使用、无数据、搜索无结果时的引导

**关键原则：**

- 每个页面只做一件事
- 减少用户决策负担（希克定律）
- 遵循用户心智模型，而非系统架构
- 提供即时反馈，让用户知道发生了什么

### 2.2 PRD（产品需求文档）

**核心结构：**

```markdown
# [功能名称] PRD

## 1. 背景与目标
- 为什么做？解决什么问题？
- 成功标准是什么？（可量化的指标）

## 2. 用户故事 / 使用场景
- 谁在什么场景下做什么？

## 3. 功能描述
- 功能列表（P0/P1/P2）
- 业务规则
- 交互说明（附原型链接）

## 4. 数据需求
- 需要哪些数据输入？
- 数据从哪来？格式？质量要求？

## 5. 异常处理
- 各种异常场景及对应策略

## 6. 权限设计
- 不同角色的可见/可操作范围

## 7. 非功能性需求
- 性能要求、安全要求、兼容性要求

## 8. 排期与里程碑
- 开发、测试、上线时间节点
```

### 2.3 原型设计

**工具选择：**

| 保真度 | 工具 | 适用阶段 |
|--------|------|----------|
| 低保真 | 纸笔、白板 | 头脑风暴、快速验证想法 |
| 中保真 | Balsamiq、Axure | 流程验证、需求评审 |
| 高保真 | Figma、Sketch | 视觉确认、用户测试 |

**原型设计原则：**

- 先结构后细节：信息架构 → 页面布局 → 交互细节
- 标注清晰：尺寸、颜色、字体、交互状态（hover/active/disabled）
- 覆盖完整：正常状态 + 空状态 + 加载状态 + 错误状态 + 边界情况

### 2.4 异常流程设计

**必须考虑的异常场景：**

| 类型 | 示例 | 设计策略 |
|------|------|----------|
| 网络异常 | 断网、超时 | 离线缓存、重试机制、明确提示 |
| 数据异常 | 空数据、格式错误、超长文本 | 默认值、输入校验、截断/换行策略 |
| 权限异常 | 未登录、无权限、token 过期 | 引导登录、权限申请、静默刷新 |
| 并发冲突 | 多人同时编辑 | 乐观锁/悲观锁、冲突提示与解决 |
| 业务异常 | 库存不足、余额不够 | 前置校验、替代方案引导 |
| AI 异常 | 模型超时、结果不可靠 | 降级策略、置信度展示、人工兜底 |

### 2.5 权限设计

**常见权限模型：**

- **RBAC（基于角色）**：用户 → 角色 → 权限（最常用）
- **ABAC（基于属性）**：根据用户属性、资源属性、环境条件动态判断
- **数据权限**：控制用户能看到哪些数据范围（部门、项目、个人）

**设计要点：**

- 功能权限：菜单可见性、按钮可操作性
- 数据权限：行级（哪些记录）、列级（哪些字段）
- 默认策略：最小权限原则，按需开放

## 3. 优先级排序

> 核心目标：在有限资源下，做最有价值的事。

### 3.1 常用优先级框架

**RICE 评分法**

```
RICE Score = (Reach × Impact × Confidence) / Effort

- Reach（覆盖范围）：这个功能影响多少用户？
- Impact（影响程度）：对每个用户的影响有多大？(3=大/2=中/1=小/0.5=极小)
- Confidence（信心水平）：对上述估计有多大把握？(100%=高/80%=中/50%=低)
- Effort（工作量）：需要多少人月/人周？
```

**Kano 模型**

```
           满意度 ↑
                  |    兴奋型需求（Delighters）
                  |   /
                  |  /  期望型需求（Performance）
                  | /  /
                  |/  /
    ——————————————/——————————————→ 功能完善度
                  |/
                  |  基本型需求（Must-be）
                  |
```

**MoSCoW 法**

| 级别 | 含义 | 判断标准 |
|------|------|----------|
| Must have | 必须有 | 没有它产品无法上线/无法使用 |
| Should have | 应该有 | 重要但非必须，可以延后 |
| Could have | 可以有 | 锦上添花，资源充足时做 |
| Won't have | 暂不做 | 明确排除，避免范围蔓延 |

### 3.2 多维度评估矩阵

| 维度 | 权重建议 | 评估问题 |
|------|----------|----------|
| 用户价值 | 30-40% | 解决多大痛点？影响多少用户？频率多高？ |
| 商业价值 | 20-30% | 对营收/增长/留存有什么贡献？ |
| 实现成本 | 20-30% | 开发需要多久？技术复杂度？维护成本？ |
| 风险 | 10-20% | 技术风险？合规风险？市场风险？ |

### 3.3 AI 产品的特殊考量

- **数据就绪度**：有足够高质量的数据来训练/微调模型吗？
- **技术可行性**：当前模型能力能否满足产品需求？需要多少实验验证？
- **迭代成本**：AI 功能上线后，调整/回滚的成本有多高？
- **用户信任**：功能是否需要用户信任 AI 决策？建立信任需要多少投入？

### 3.4 实战建议

- **不要追求完美排序**：80% 准确的快速排序 > 100% 精确的缓慢排序
- **定期回顾**：每 2 周重新评估一次优先级，根据新信息调整
- **学会说不**：资源有限，每个"是"都意味着对其他需求说"不"
- **对齐利益相关者**：排序结果需要和团队、管理层达成共识

## 4. 指标体系

> 核心目标：用数据驱动产品决策，衡量产品是否成功。

### 4.1 指标层次

```
                    ┌─────────────────┐
                    │  北极星指标 (NSM) │  ← 一个最关键的指标
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
        ┌─────┴─────┐  ┌─────┴─────┐  ┌─────┴─────┐
        │ L1 核心指标 │ │ L1 核心指标 │ │ L1 核心指标 │  ← 驱动 NSM 的关键因子
        └─────┬─────┘  └─────┬─────┘  └─────┬─────┘
              │              │              │
         ┌────┴────┐    ┌────┴────┐    ┌────┴────┐
         │L2 过程指标│    │L2 过程指标│    │L2 过程指标│  ← 可执行、可优化的具体指标
         └─────────┘    └─────────┘    └─────────┘
```

### 4.2 北极星指标（North Star Metric）

**定义：** 一个能最好地衡量产品给用户核心价值的指标。

**好的北极星指标特征：**

- 反映用户获得的价值
- 是业务增长的先行指标
- 可操作、可衡量、可拆解
- 全团队能对齐理解

**常见产品的北极星指标示例：**

| 产品类型 | 北极星指标 | 原因 |
|----------|-----------|------|
| 电商 | GMV / 周活跃购买用户数 | 衡量交易规模 |
| 社交 | DAU × 日均互动次数 | 衡量社区活跃度 |
| SaaS | 周活跃使用时长 / 核心功能使用率 | 衡量产品价值交付 |
| 内容平台 | 日均阅读/观看时长 | 衡量内容消费深度 |
| AI 工具 | 任务完成率 / AI 建议采纳率 | 衡量 AI 实际帮到用户的程度 |

### 4.3 漏斗指标

**用户生命周期漏斗：**

```
获取 → 激活 → 留存 → 变现 → 推荐
(A)    (A)    (R)    (R)    (R)
```

**关键漏斗指标：**

| 阶段 | 核心指标 | 计算方式 |
|------|----------|----------|
| 获取 | 注册转化率 | 注册数 / 访问数 |
| 激活 | 首次关键行为完成率 | 完成核心操作的用户 / 注册用户 |
| 留存 | 次日/7日/30日留存率 | 第N日回访用户 / 第0日新增用户 |
| 变现 | 付费转化率、ARPU | 付费用户 / 活跃用户、人均收入 |
| 推荐 | NPS、K-factor | 推荐意愿评分、病毒系数 |

**AARRR vs RARRA：**

传统 AARRR 以获取为中心，但现代产品更关注留存优先（RARRA）：

```
Retention → Activation → Referral → Revenue → Acquisition
  留存  →    激活    →   推荐   →   变现   →   获取
```

### 4.4 功能成功标准

**每个功能上线前必须定义成功标准：**

```markdown
## [功能名称] 成功标准

### 核心指标
- 指标名称：[如：功能使用率]
- 当前基线：[如：0%（新功能）]
- 目标值：[如：上线30天后达到 20% DAU]
- 衡量周期：[如：30天]

### 辅助指标
- [如：使用该功能的用户留存率 vs 未使用用户]
- [如：功能满意度评分 > 4.0/5.0]

### 护栏指标（不能恶化）
- [如：页面加载时间 < 2s]
- [如：核心流程完成率不下降]

### 决策规则
- 达标：继续投入优化
- 部分达标：分析原因，决定是否迭代
- 未达标：复盘并决定是否下线
```

### 4.5 AI 产品的特殊指标

| 维度 | 指标 | 说明 |
|------|------|------|
| 模型效果 | 准确率/召回率/F1 | 根据业务场景选择合适的指标 |
| 用户体验 | 任务完成率、AI 建议采纳率 | 用户是否真的在用 AI 的输出 |
| 信任度 | 用户修改 AI 结果的比例 | 修改率越低，信任度越高 |
| 效率提升 | 使用前后耗时对比 | AI 是否真的帮用户省了时间 |
| 成本 | 单次调用成本、日均成本 | 商业可持续性 |
| 安全 | 有害输出率、幻觉率 | 风险控制底线 |

### 4.6 指标体系搭建实战

**步骤：**

1. **明确产品目标**：这个阶段最重要的事是什么？
2. **定义北极星指标**：什么指标最能衡量目标达成？
3. **拆解驱动因子**：北极星指标 = f(因子1, 因子2, ...)
4. **设定过程指标**：每个因子对应什么可操作的指标？
5. **建立监控看板**：实时/每日/每周追踪
6. **设定预警阈值**：指标异常时自动告警
7. **定期回顾迭代**：指标是否仍然反映真实情况？

## 总结

产品基本功的四项能力相互关联：

```
需求分析 → 产品设计 → 优先级排序 → 指标体系
  │           │           │           │
  │           │           │           └── 验证需求是否正确
  │           │           └── 决定先做什么
  │           └── 定义怎么做
  └── 明确做什么、为什么做
```

**持续精进建议：**

- 每个需求多问三个"为什么"，挖到真实痛点
- 设计时先画流程再画界面，先想异常再想正常
- 排序时用数据说话，避免"声音最大的人赢"
- 上线不是终点，而是验证假设的起点
